## Customer Credit & Customer Resolution Framework (Version 2.3)

**Architecture complete; Phase 3.0 (`CustomerCreditService` foundation) and Phase 3.1 (Customer Credit Administration UI) are both complete.** This is a separate, independently-deployable initiative from the core `LedgerBalanceService` consolidation track — it does not block, and is not blocked by, Phase 2.8B. Four architecture documents exist: `CUSTOMER_CREDIT_ARCHITECTURE.md`, `CUSTOMER_RESOLUTION_ARCHITECTURE.md`, `PROMOTIONAL_CREDIT_ARCHITECTURE.md`, `GIFTCARD_ARCHITECTURE.md`, plus a dedicated tracker, `CUSTOMER_CREDIT_TODO.md`. Highlights:

- `CustomerCreditService` (`app/Services/CustomerCreditService.php`) implements Financial Credit `createFinancialCredit()`, `redeem()`, `canRedeem()`, `remainingBalance()`, `history()`, against a **new, wholly separate `customer_credits` table** — not `customer_accounts`, and with **zero dependency on `LedgerBalanceService`/`CustomHelper`/`TaxCalculationService`**, confirmed via source search. This is a deliberate refinement of the original architecture proposal: reusing the dormant `customer_accounts.type='credit'`/`'debit'` values remains the right *future* integration, gated on `LedgerBalanceService` itself being ready to support it — not done in this phase, per its explicit "manages assets, not debt — do not blur these responsibilities" instruction.
- **Phase 3.1 built the internal administration UI**: a sixth CRM customer-record tab (summary cards, Grant/Redeem dialogs, filterable/sortable history), gated by 6 new permissions enforced via Spatie's `permission:` route middleware — the first real caller of that already-registered-but-unused infrastructure anywhere in this codebase. Validated with genuine authenticated/permission-checked rendering (both positive and negative paths) plus a real route-middleware enforcement check, not just template compilation.
- **Phase 3.1 discovered two genuine, previously-unknown pre-existing defects** in `ModuleSeeder`'s shared logic (`modules.need_set_permissions` and `permissions.permission_to_all`, both `NOT NULL` with no default anywhere — reproduced against the untouched, pre-existing `personnel` module to confirm they predate this phase). **These block deploying Phase 3.1's new permissions in any environment until fixed** — documented as an Outstanding Risk in `docs/customer-credit/PHASE_3_1_COMPLETION_REPORT.md`, not fixed, per that phase's "no unrelated fixes" rule.
- Deliberately keeps the new Customer Credit balance separate from `customers.available_credit_balance`, to avoid deepening the "running balance vs. available credit" ambiguity `PHASE_2_5A_LEDGER_READINESS_REVIEW.md` already flagged.
- Grounded in real, confirmed-existing infrastructure discovered during research across both phases: `CustomHelper::getCustomerAccountStatus()` (`Good Standing`/`Bad Debt` + aging alerts, already live), the real Order Edit screen (no admin checkout screen exists — orders are created via front-end checkout only), the two already-separate refund mechanisms (ledger vs. gateway), and mature SMS (`TwilioService`)/Email (`EmailTemplate`) infrastructure reusable for Promotional Credit campaigns.
- Gift Cards are confirmed greenfield (zero existing infrastructure) and are designed to reuse the Customer Credit redemption engine, isolating only the genuinely different parts (issuance-as-a-sale, code-based identity, an unresolved legal/expiration question flagged as the framework's single highest-priority open item).
- **Zero changes to `LedgerBalanceService`, `CustomHelper`, or any core-track file were made in either Phase 3.0 or Phase 3.1.**

## The Financial Truth Table

**`docs/financial-engine-consolidation/FINANCIAL_TRUTH_TABLE.md` is now the single authoritative accounting-policy reference for the Financial Engine.** Every future Financial Engine service (`LedgerBalanceService`, `FinancialReportingAdapter`, any future Customer Balance Service, any future accounting integration) must *implement* this document, never define new business policy itself. If a gap is found, it must be added there first (as an amendment, with business/technical sign-off recorded in `FINANCIAL_DECISIONS.md`), before any code implements it.

## LedgerBalanceService Status

**Arithmetic and write-path foundation complete and independently validated (Phases 2.6, 2.6A, 2.7); real caller migration has now begun (Phase 2.8A).** `app/Services/LedgerBalanceService.php` implements `amountWithTax()` (Phase 2.6) and `applyTransaction()` (Phase 2.7) for Payment, Order, and Charge (Manual/Fuel/Damage — one shared code path); Extension Charge is served by `amountWithTax()` alone. Every deferred type throws a `\LogicException` naming the exact `FINANCIAL_TRUTH_TABLE.md` row that blocks it. Neither method was modified in Phase 2.8A.

This gates Charge-family migration only.

**Phase 2.8A migrated the first real production callers.** Every one of the 19 active `CustomHelper::updateCreditBalance()` call sites was read in full context (`PHASE_2_8A_PRE_MIGRATION_AUDIT.md`). **7 create only a hardcoded `payment` or `order` type and were migrated** to `LedgerBalanceService::applyTransaction()` — a one-line swap per call site: `CustomerAccount/PaymentStoreController.php`, `Invoice/PaymentStoreController.php` (admin), `Dashboard/PaymentStoreController.php`, `Front/Customer/Dashboard/Invoice/PaymentStoreController.php`, `ChargeService::recordPayment()`, `OrderManagement/Orders/AddToAccountPaymentController.php`, `Front/Checkout/PostController.php`. **12 remain excluded**: 8 deferred-family (Refund, Discount, Charge), 4 type-ambiguous regardless of family (`CustomerAccount/UpdateController.php` — edits any existing type, also depends on the unbuilt `reverseTransactionEffect()`; `Invoice/StoreController.php` and `Invoice/UpdateController.php`'s two call sites — each dynamically creates `charge`/`discount`/`refund`/`order` from one shared `if`/`elseif` chain). Post-migration repository-wide search confirmed a clean 7/12 split — zero mixed or accidental migrations.

**Zero-caller status is now specific, not blanket**: `CustomHelper::updateCreditBalance()` is referenced only by the 12 deferred/ambiguous call sites; `LedgerBalanceService::applyTransaction()` is referenced only by the 7 approved Payment/Order callers. Full detail in `PHASE_2_6_COMPLETION_REPORT.md`, `PHASE_2_6A_PARALLEL_VALIDATION_REPORT.md`, `PHASE_2_7_COMPLETION_REPORT.md`, `PHASE_2_7A_ROUNDING_INVESTIGATION.md`, `PHASE_2_8A_PRE_MIGRATION_AUDIT.md`, and `PHASE_2_8A_COMPLETION_REPORT.md`.

**Migrating the remaining 8 deferred-family callers (Phase 2.8B) is still gated** on resolving the items marked "Needs Business Decision" or "Needs Technical Decision" in `FINANCIAL_TRUTH_TABLE.md` §7, **plus the still-unresolved Phase 2.7A question**: a MySQL-backed re-validation of the `'charge'`+`'add'` sub-case, or an explicit, documented decision to accept the residual risk without one. The 4 type-ambiguous call sites additionally require `reverseTransactionEffect()`'s `LedgerBalanceService` equivalent to be built before they can even be considered.
