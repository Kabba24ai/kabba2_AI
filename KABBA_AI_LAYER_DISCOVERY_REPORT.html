Files To Be Created

Every proposed new file with justification for why it cannot reuse an existing file.

D1. Migration

Filedatabase/migrations/YYYY_MM_DD_create_ai_page_metadata_table.php
JustificationStores cached generated AI metadata. Avoids regenerating JSON-LD on every page load. Enables hash-based change detection — metadata only regenerates when source data actually changes. Enables the Artisan backfill command for existing records.

D2. Eloquent Model

Fileapp/Models/AIVisibility/AiPageMetadata.php
JustificationStandard model for the new table. Enables type-safe querying and upsert operations from services.

D3. Service — AIPageMetadataGenerator

Fileapp/Services/AIVisibility/AIPageMetadataGenerator.php
JustificationCentral orchestrator. Accepts a model instance, pulls existing SEO + content fields, computes hash, skips regeneration if unchanged, calls SchemaBuilder, saves result. Single entry point keeps generation logic out of Observers and controllers.
Public methodsgenerateForProduct(Product $p), generateForCategory(ProductCategory $c), generateForHome()

D4. Service — SchemaBuilder

Fileapp/Services/AIVisibility/SchemaBuilder.php
JustificationSchema assembly is a distinct concern from orchestration. Returns PHP arrays that become JSON-LD. Each method is independently testable. Separated so future AI enrichment can be added to specific methods without touching orchestration logic.
Methods buildProductSchema(Product) → schema.org/Product
buildRentalOfferSchema(Product) → schema.org/Offer per rental period
buildRetailOfferSchema(Product) → schema.org/Offer
buildCategorySchema(ProductCategory) → schema.org/Service or ItemList
buildBreadcrumbSchema(array $crumbs) → schema.org/BreadcrumbList
buildOrganizationSchema() → schema.org/Organization from Settings
buildLocalBusinessSchema(Store) → schema.org/LocalBusiness
buildFAQSchema(Collection $faqs) → schema.org/FAQPage

D5. Observer — ProductObserver

Fileapp/Observers/ProductObserver.php
JustificationAutomatically triggers metadata regeneration when a product is saved or deleted. Zero manual intervention required from the admin.

Section H

Risk Assessment

Every risk considered, with mitigation for each.

RiskLevelMitigation
Breaking existing product pages None No existing code removed. The @push('schema') block is entirely new and separate from @push('meta').
Breaking existing category pages None Same — additive only.
Breaking existing SEO meta tags None The existing @push('meta') blocks are untouched. New stack is schema, not meta.
Invalid JSON-LD crashing the page Low JSON-LD lives in a <script> tag, not in page body. Invalid JSON inside a script tag does not cause visible errors or break page rendering. Additionally, json_encode() with JSON_THROW_ON_ERROR catches malformed data before output.
Performance impact on page load Low Metadata is cached in the DB. A page load performs one indexed lookup. On-the-fly generation only happens once per product/category (cache miss). All subsequent requests read from cache.
Admin workload increase None Zero new required fields. All metadata is derived automatically from existing content. Admins manage the same forms they always have.
External AI service dependency None Version 1 is 100% deterministic — no OpenAI, Claude, or any external API. All schema is generated from existing Kabba database records.
Duplicate or conflicting SEO systems None The AI layer does not replace or shadow the existing SEO fields. It reads from them as source data. One source of truth — multiple outputs.
Keyword stuffing / spam penalties None Output is valid JSON-LD in <script> tags (standard practice endorsed by Google). No hidden text in page body. No fake reviews, ratings, or inventory.
ℹ️
Reversibility: If the feature needs to be disabled, removing the three @push('schema') additions from the Blade templates (11 total lines) completely disables all AI layer output. The website continues functioning normally. The ai_page_metadata table remains but is simply unused.
