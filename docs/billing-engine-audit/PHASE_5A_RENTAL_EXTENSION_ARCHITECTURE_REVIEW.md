# Phase 5A — Rental Extension Architecture Review

**Branch:** `feature/billing-engine-consolidation`
**Date:** 2026-06-27
**Status:** Architecture review only — no code changes in this phase

---

## Purpose

Before bridging rental extensions into BillingEngine, this document audits the complete extension workflow, identifies the suffix generation bugs, and establishes the architectural decisions that will govern Phase 5B (bridge implementation).

---

## 1. Current Extension Workflow

When an admin creates a rental extension charge from the Order Edit page:

1. The existing parent order is looked up via `unique_id` route param
2. A suffix letter (A, B, C…) is generated by counting existing extensions
3. A new child `Order` is created with `order_number = "{parent}-{suffix}"`
4. A pending `OrderPayment` is written to the child order
5. An optional `OrderNote` is written to the child order
6. The billing address is copied from the parent order to the child order
7. An `OrderHistory` entry is written on the PARENT order
8. The response returns JSON with the child order's `unique_id`, `order_number`, and an `edit_url`

## 4. Child Order Creation

Extension orders are full `Order` rows. Key fields:

| Field | Value |
|-------|-------|
| `order_number` | `"{parent_order_number}-{suffix}"` e.g. `#1668-A` |
| `reference_order_number` | `$order->order_number` (FK → parent order) |
| `customer_id` | Copied from parent |
| `customer_name`, `email`, `phone`, `company_name` | Copied from parent |
| `subtotal` | `$baseAmount` |
| `tax_amount` | `$taxAmount` (0 if `add_tax = false`) |
| `grand_total` | `$baseAmount + $taxAmount` |
| `is_tax_exempt` | `'No'` if taxed, `'Yes'` if not |
| `order_note` | `$validated['description']` |

The child order does NOT have:
- `order_date` explicitly set (the model boot sets it to today)
- `created_by_id` / `created_by_type` morphs (these are nullable on the extension path — `StoreController` does not pass them to `Order::create()`)
- `order_products` rows
- `terms_*` fields

## 5. Parent / Child Relationship

```
orders.reference_order_number (nullable) → orders.order_number (FK)
```

- The **extension child** sets `reference_order_number = parent.order_number`
- The **parent** has `reference_order_number = null`
- **Reorders** (front-end checkout with `session('order.type') === 'existing_order'`) also set `reference_order_number` to the parent order number but receive a new sequential `order_number` (not suffixed)

Relationship methods on `Order`:
```php
public function referenceOrder()   // belongs to parent via reference_order_number
public function relatedOrders()    // has many via reference_order_number → order_number
```

## 6. Suffix Generation — Current Logic and Bugs

### Current code (`StoreController`, lines 29–35)

```php
$existingCount = Order::where('reference_order_number', $order->order_number)->count();
if ($existingCount >= 26) { ... }  // max 26 extensions
$suffix = chr(65 + $existingCount); // A=65, B=66, ...
$extensionOrderNumber = $order->order_number . '-' . $suffix;
```

### Bug 1: Reorder inflation (non-fatal, wrong suffix)

**Root cause:** `Order::where('reference_order_number', ...)` counts ALL orders whose `reference_order_number` matches — including front-end reorders. Reorders get a new sequential `order_number` (e.g., `#1670`) and set `reference_order_number = '#1668'`. They are NOT extensions, but the count includes them.

**Consequence:** If 2 reorders exist for `#1668`, the first extension creation sees `count = 2` and generates suffix `C` instead of `A`. The extension is created as `#1668-C`, skipping A and B. No crash, but confusing numbering.

### Bug 2: Soft-delete collision (fatal — 500 error)

**Root cause:** `Order::where(...)` uses the `SoftDeletes` trait, which automatically excludes soft-deleted rows. If extension `#1668-A` is soft-deleted, the count drops to 0. The suffix logic generates `A` again.

**Consequence:** `orders.order_number` has a `UNIQUE` constraint. Soft-deleted rows still occupy their unique slot. Attempting to insert a second `#1668-A` raises a SQL unique constraint violation, causing the controller's `catch (\Throwable $e)` to return HTTP 500. The admin sees: "Failed to create extension charge. Please try again." — the real cause is invisible.

### Recommended fix (Phase 5B)

```php
$existingCount = Order::withTrashed()
    ->where('reference_order_number', $order->order_number)
    ->where('order_number', 'like', $order->order_number . '-%')
    ->count();
```

Two changes:
1. `withTrashed()` — includes soft-deleted extensions in the count, preventing unique constraint collisions. Soft-deleted `#1668-A` remains slot A permanently; the next extension gets `B`. This is the correct behavior for an audit trail.
2. `->where('order_number', 'like', $order->order_number . '-%')` — excludes reorders (which have non-suffixed `order_number` values like `#1670`). Matches the filter already used in `EditController:60-62`.

**Note:** This filter is already applied in `EditController` for display purposes:
```php
$relatedOrders = Order::where('reference_order_number', $order->order_number)
    ->where('order_number', 'like', $order->order_number . '-%')  // excludes reorders
    ->with([...])
    ->latest('id')
    ->get();
```

The suffix generation simply needs to match this same filter.

### Where should the suffix logic live?

**Recommendation: `OrderExtensionService`** (not BillingEngine).

The suffix is an order numbering concern, not a billing concern. BillingEngine's responsibility is to record a `billing_charges` row — it should not know how order numbers are formatted.

A thin `OrderExtensionService::createExtension(Order $parent, array $validated, User $user): Order` service would:
1. Determine the suffix using the fixed count query
2. Create the child order with all related records
3. Return the child order

`StoreController` calls the service, then calls `BillingEngine::charge()` with the returned child order. This keeps suffix logic testable and reusable if extensions are ever triggered from mobile or API contexts.

## 7. Payment Behavior

A `Pending COD` payment is created on the child order at extension creation time:

```php
$extension->payments()->create([
    'payment_datetime' => now(),
    'payment_method'   => OrderPaymentMethod::COD->value,
    'amount'           => $grandTotal,
    'status'           => OrderPaymentStatus::Pending->value,
    'created_by_id'    => $user->id,
    'created_by_type'  => User::class,
]);
```

This payment record drives:
- `Order::getIsPaidAttribute()` → false until a Paid payment exists
- `Order::getLastPaymentStatusAttribute()` → `'Pending'`
- The order appearing as "Pending" in the Orders index and schedule views

The admin manually updates the payment status later (via the existing payment UI on the extension order's edit page). The extension controller creates no invoice, no charge to the customer's card, and no receipt.

## 8. Tax Behavior

Tax is calculated at extension creation time using the global sales tax rate from configuration:

```php
$salesTaxRate = (float) (ConfigurationHelper::getSettings(null, 'sales_tax') ?? 0);
$taxAmount    = $validated['add_tax'] ? round($baseAmount * $salesTaxRate, 2) : 0.00;
$grandTotal   = $baseAmount + $taxAmount;
```

Stored on the child order:
- `subtotal` = `$baseAmount`
- `tax_amount` = `$taxAmount`
- `grand_total` = `$grandTotal`
- `is_tax_exempt` = `'No'` / `'Yes'`

No per-line-item tax. No `customer_accounts.sales_tax_type` field. The tax decision is binary (`add_tax: true/false`) at creation time.

**BillingEngine mapping:**
- `tax_type`: `'add'` if `$validated['add_tax'] === true`, else `'free'`
- `tax_amount`: `$taxAmount`
- `amount`: `$baseAmount` (pre-tax)

## 10. Recommended BillingEngine Mapping

### Strategy: Option C — `billing_charges` row + child order

**Option A (billing_charges only):** Rejected. The child order is required for payment tracking, accounting, reporting, receipt generation, and tax records. You cannot remove it.

**Option B (child order only):** Rejected. BillingEngine would have no visibility into the extension charge, defeating the consolidation purpose.

**Option C (billing_charges + child order):** Correct. The child order remains the source of truth for accounting. The `billing_charges` row provides BillingEngine visibility, audit trail, and the consolidated charge history view that Phase 7 will build.

`billing_charges.child_order_id` already exists in the schema (migration `2026_06_27_000001_create_billing_charges_table.php`, line 26). It was designed specifically for this case.

## 12. Idempotency Key Design

Format: `rental_extension:{extension_order_id}`

**Why `extension_order_id` and not the parent order ID:**
- An extension `order_id` is unique per extension
- The parent order can have multiple extensions (A, B, C…) — using the parent ID would create collisions between extensions
- `extension_order_id` is set during the same `DB::transaction`, so it's available before the BillingEngine call

**Why not `extension_order_number`:**
- Numbers like `#1668-A` could theoretically be re-used if an extension is soft-deleted and the fix described in §6 is not yet applied
- The `id` auto-increment is immutable and guaranteed unique even across soft-deletes

## 13. Risks Before Implementation

### Risk 1: Suffix bug must be fixed in the same PR as the bridge

The soft-delete collision bug (§6, Bug 2) will cause `StoreController` to throw before the BillingEngine bridge is ever reached. If the suffix fix is not applied at the same time as the bridge, testing will be blocked by random 500 errors when test extensions are soft-deleted.

**Mitigation:** Fix the suffix count query in Phase 5B alongside the bridge.

### Risk 2: `StoreController` does not pass `created_by_id`/`created_by_type` to `Order::create()`

The extension `Order` row is created without morph fields. If the `orders` table ever makes these non-nullable, extension creation will fail. Currently the original `create_orders_table` migration defines them as required morphs (non-nullable), but the extension order creation does not pass them. This may work today only because the columns were later made nullable or because the morph constraint is not enforced at the model level.

**Mitigation:** Check the current migration state of `created_by_id`/`created_by_type`. If nullable, no action needed now — document and add to tech debt log.

### Risk 3: `BillingCharge.parent_order_id` and extension orders

For extension charges, `parent_order_id` refers to the ORIGINAL order, not the extension order. For all other charge types, `parent_order_id` typically refers to the order context for the charge. For extensions, that "context order" is the parent — the extension IS the `child_order_id`. The field semantics are consistent.

### Risk 4: Extension order has no `created_by` morphs

`StoreController` creates the extension via `Order::create([...])` without passing `created_by_id`/`created_by_type`. The BillingEngine `billing_charges.created_by_id` will be set from `auth()->id()` (or not set) — this is not a blocker but should be confirmed in Phase 5B.
