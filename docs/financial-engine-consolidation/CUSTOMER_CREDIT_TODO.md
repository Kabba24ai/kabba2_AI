# Customer Credit & Customer Resolution — Project Tracker

Last updated: 2026-07-06 (after Phase 3.6 — Customer Resolution Operations Center)
This is a permanent, living tracker for the Customer Credit / Customer Resolution / Promotional Credit / Gift Card initiative — a separate, independently-deployable initiative that integrates with, but does not replace or block, the core Financial Engine consolidation tracked in `FINANCIAL_ENGINE_TODO.md`. This initiative uses its own phase numbering ("Customer Credit Platform Phase N.N") distinct from "Financial Engine Version N.N" in the core tracker. **Phase 3.1 and later documents live under `docs/customer-credit/`, a new directory distinct from `docs/financial-engine-consolidation/`** (where this tracker and the architecture docs live, and where Phase 3.0's documents live) — noted here since the location itself changed starting this phase. **Platform Stabilization Sprint 1 lives under `docs/platform/`** — a third directory, since it is platform-wide infrastructure work, not specific to this initiative, even though it was discovered and unblocked by it.

## Key Architectural Decisions Made in This Phase

1. ~~Customer Credit reuses the dormant `customer_accounts.type = 'credit'`/`'debit'` enum values~~ — **this was the original proposal; Phase 3.0 built a separate `customer_credits` table instead** (see the Phase 3.0 revision note above). The dormant enum values remain exactly as undefined as `PHASE_2_5A_LEDGER_READINESS_REVIEW.md` and `FINANCIAL_TRUTH_TABLE.md` §3b rows 4-5 already documented — this initiative has not yet resolved that gap, only worked around needing to resolve it immediately.
2. **Customer Credit balance is a distinct figure from `customers.available_credit_balance`** — deliberately not conflated with the existing running-balance field, to avoid deepening the "Customer Balance vs. Available Credit" ambiguity `PHASE_2_5A_LEDGER_READINESS_REVIEW.md` already flagged.
3. **Gift Cards get their own table**, not an overload of `customer_accounts`, because a gift card's identity (its code) exists independently of any customer record — but redemption reuses the same `LedgerBalanceService` path as any other credit.
4. **`CustomerCreditService` is the only component authorized to write to the Customer Credit ledger** — `PromotionalCreditService` and the future `GiftCardService` are expected to call into it rather than writing directly to its storage, preserving the "who decides vs. who writes" separation this initiative has maintained since Phase 2.1. **Superseded detail, corrected in Phase 3.0**: that storage is `customer_credits`, a new table built for this purpose — not `customer_accounts`'s `credit`/`debit` rows, which remain untouched and exactly as undefined as `FINANCIAL_TRUTH_TABLE.md` already documents. See the Phase 3.0 revision note above for why.
5. **The Resolution Wizard's Order Entry integration targets the real, existing Order Edit screen** (`OrderManagement/Orders/EditController.php`), not a hypothetical admin checkout screen — confirmed during this phase's research that no such screen exists; orders are created via front-end checkout only.
6. **The "Customer Status" panel extends, not replaces,** the already-existing `CustomHelper::getCustomerAccountStatus()` (`Good Standing`/`Bad Debt` + aging alerts) — "Past Due" is a reframing of the existing aging-alert states; "Payment Plan" is the one genuinely new status requiring a feature that doesn't exist yet.

## Open Business Decisions (see each architecture document's own "Open Business Decisions" section for full detail)

- Does Financial Credit ever expire (escheatment/unclaimed-property law)?
- Redemption order when a customer holds both Financial and Promotional credit.
- Tax treatment of credit grants and redemptions — a new row this initiative would need to add to `FINANCIAL_TRUTH_TABLE.md`, with business sign-off, before any implementation.
- Exact schema for distinguishing Financial vs. Promotional credit.
- Per-employee dollar authority ceilings for the Resolution Wizard's Store Credit and Refund offers.
- Manager Override pattern-detection threshold (repeat-resolution customers).
- Marketing-consent/opt-out policy for Promotional Credit campaigns.
- Gift Card expiration and legal/compliance treatment — **the single highest-priority open item across all four documents**, since many US states restrict gift card expiration in ways that do not apply to ordinary promotional credit.
- Gift Card transfer model (informal code-based vs. formal registered transfer).

## Open Technical Decisions

- ~~Whether Customer Credit balance is computed live from `customer_accounts` or maintained as a running total in a dedicated table~~ — **resolved by Phase 3.0**: computed live from the new `customer_credits` table (`sum(grants) − sum(redemptions)`), never cached.
- Exact column/table design for `credit_category` (Financial vs. Promotional) — a column addition vs. a new table vs. a reason-string convention. **Still open** — `customer_credits` (Phase 3.0) has no such column yet, since Promotional Credit doesn't exist to need one.
- Whether the Resolution Wizard is a new set of Blade views/controllers or a modal-driven addition to the existing Order Edit screen.
- New permission keys needed for: granting credit, applying already-granted credit, approving a manager override, and creating a campaign — these should be distinct permissions, not one shared permission, per `CUSTOMER_RESOLUTION_ARCHITECTURE.md` §8's explicit "granting vs. applying" separation.
