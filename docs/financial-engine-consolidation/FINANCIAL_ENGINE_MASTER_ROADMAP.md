## 1. Executive Summary

Kabba's financial calculations — payment amounts, tax, running balances, invoice totals, and revenue reporting — currently live in more than a dozen independent implementations spread across helper classes, controllers, Blade views, and reporting engines. These implementations were each written correctly for their own moment in time, but because they were never unified, they have quietly drifted apart. The result is a system where the same underlying fact — "how much did this customer pay, and how much of it was tax" — can be computed two, three, or even six different ways depending on which screen or report happens to be asking.

This is not a hypothetical risk. It is how a confirmed, customer-visible bug reached production: a $150.00 payment, processed correctly and recorded correctly in the ledger, displayed as $164.63 on the CRM Billing Summary page because one of the many places that compute "payment plus tax" used the wrong formula for that specific screen. The ledger was never wrong. The display was. That distinction — correct data, inconsistent presentation and reporting — is the exact failure mode this initiative exists to eliminate permanently, not just patch once.

A second, independently discovered instance of the same failure mode — Dashboard revenue totals using an incorrect tax formula relative to the Sales Tax and Pure Sales Summary reports — surfaced during the architecture analysis for this initiative, before any consolidation work began. This confirms the underlying problem is structural, not a single one-off mistake: as long as financial logic is duplicated, it will continue to drift, and each drift will surface as a new, unrelated-looking bug in a different part of the product.

Financial consistency is not a cosmetic concern at Kabba. Billing Summary, Customer Credit Accounts, Invoicing, the Billing Engine (post-order charges), Sales Reports, and Dashboard Reporting all describe the same underlying money. Customers, staff, and — eventually — external systems like QuickBooks and customer-facing statements all need to see the same number for the same fact, every time. When they don't, the cost is not just an incorrect screen; it is eroded trust in every other number the system reports, because there is no way to know from the outside which numbers are the reliable ones.

The Financial Engine initiative exists to make that distinction unnecessary: to build a small set of shared, authoritative services that every financial screen, report, and future integration calls into, so that "correct" and "consistent" become the same property instead of two properties that have to be separately verified.

## 2. Vision

**The long-term objective is a single Financial Engine: one authoritative source of truth for every financial calculation performed anywhere in Kabba.**

In the end state:

- There is exactly one place in the codebase that knows how to compute a tax breakdown, a running balance, an invoice total, or a payment allocation.
- Every consumer of a financial number — the CRM, the Credit Account ledger, Invoicing, the Billing Engine, Sales Reports, Dashboard Reporting, and future systems such as QuickBooks export and Customer Statements — calls the same underlying service to get that number, rather than deriving it independently.
- Two screens showing "the same" financial fact are structurally guaranteed to agree, because they are backed by the same calculation, not by two calculations that happen to have been kept in sync by hand.
- New financial features are built by composing existing, trusted services rather than by writing new bespoke math, which means new features inherit correctness instead of re-risking it.

This vision is deliberately architectural, not aspirational. It does not mean rewriting the application, changing accounting behavior, or introducing new financial features. It means relocating and unifying logic that already exists and is already, for the most part, correct — and closing the gaps where it has already drifted.

The Financial Engine is not a single class or a single pull request. It is a durable architectural property of the system: the guarantee that financial truth lives in one place, and everything else asks that place, rather than computing its own answer.

## 3. Design Principles

These principles govern every phase of this initiative, from the first line of the `TaxCalculationService` to the last legacy method removed. Any proposed change that conflicts with one of these principles should be rejected or rescoped, not exempted.

- **One Source of Truth.** Every financial value — a tax amount, a running balance, an invoice total — has exactly one authoritative calculation in the system. Every other place that needs that value calls the authoritative calculation; none re-derive it.
- **Shared Financial Services.** Financial logic lives in a small number of well-bounded services (see §5), not in controllers, Blade views, or ad hoc helper methods scattered by feature area.
- **No Duplicate Calculations.** If the same calculation appears in two places, that is treated as a defect in the architecture, whether or not it is currently producing a bug. Duplication is the precondition for drift, not a cosmetic inefficiency.
- **Consistent Financial Results Everywhere.** CRM, Credit Accounts, Invoicing, the Billing Engine, Sales Reports, and Dashboard Reporting must always reconcile with one another for the same underlying data. Disagreement between two screens describing the same fact is always a bug, never an accepted quirk of "that's just how that report works."
- **Small, Low-Risk Changes.** Consolidation happens through small, independently reviewable and mergeable phases, never broad rewrites. A phase that cannot be reviewed and rolled back on its own is scoped incorrectly.
- **Backward Compatibility.** Existing behavior is preserved unless a confirmed bug is identified and separately signed off. Consolidation is not an opportunity to silently change accounting behavior.
- **Auditability.** Every financial calculation must be traceable — it should be possible to answer "why is this number what it is" by pointing to one method and one set of inputs, not by reconstructing intent from several independent implementations.
- **Testability.** Every shared financial service is unit-testable in isolation, and every migration phase is validated against real data before and after the change, not merely assumed correct because "the tests pass."
- **Financial Accuracy Over Performance.** Where accuracy and performance are in tension, accuracy wins. Reporting engines that need SQL-level aggregation for performance must still express the same formula as the canonical service, not a faster-but-different approximation.
- **Conservative Refactoring.** No database schema changes unless absolutely necessary. No UI redesigns. No feature additions bundled into consolidation work. The initiative's job is to make existing correct behavior consistent, not to expand scope.

## 4. Current Architecture

### 4.1 Strengths

- Most of the individual calculations in the system are, in isolation, correct. The CRM Billing Audit and the Phase 2 Architecture Report both found that the underlying ledger, the running balance, and the payment gateway integration (Authorize.Net) are accurate — the confirmed defects found so far are display- and reporting-layer bugs, not data-integrity failures.
- Financial math is already substantially centralized in one class, `App\Helpers\CustomHelper`, rather than scattered arbitrarily — this is a reasonable starting point for consolidation, not a system that needs to be built from nothing.
- A precedent for the target architecture already exists and works: several Sales Reporting services (`PureSalesSummaryReport`, `SalesTrendAnalysisEngine`, `EmployeePerformanceEngine`) already delegate their revenue calculations entirely to a single engine (`SalesReportEngineV2`) rather than computing independently. This proves the "one shared service, many thin consumers" pattern is viable in this codebase today.
- A parallel, already-in-flight consolidation effort — the Billing Engine (`app/Services/BillingEngine.php`, `billing_charges` table) — has already demonstrated that this kind of careful, phased, bridge-mode migration can be executed successfully in this codebase: it is merged, in active use across eight controllers, and backed by 197 passing tests, all while preserving every existing legacy write path throughout its rollout.
- The team has already built and uses a validation tool, `FixRunningBalancesController`, that replays the entire ledger and reports drift per customer. This is exactly the kind of before/after diff tooling a consolidation of this scope needs, and it did not need to be built new — it already exists and is already trusted.

### 4.2 Weaknesses

- The "is tax already included in this amount, or does it need to be added" decision — the single most consequential piece of financial logic in the system — is implemented independently at least six times across four methods in `CustomHelper`, with documented, real disagreements on how Refunds and Discounts should be taxed.
- The per-row tax breakdown shown to users is duplicated across three (now four, including a previously undocumented site) Blade views, with no shared helper — a formula fix in one place has already been found not to have propagated to another (the exact mechanism of the confirmed Billing Summary bug).
- Two independent computations exist for "customer available balance" — one stored and incrementally updated, one live-recomputed — with no structural guarantee they agree. The existence of the `FixRunningBalancesController` repair tool is itself evidence this has already happened in production.
- Invoice `paid_amount` and `open_amount` are updated via two genuinely different code paths — an aggregation method and independent inline arithmetic in the payment controllers — confirmed during this initiative's architecture analysis to both exist and never call each other.
- The same column name, `sales_tax`, means two different things in two different tables (a rate in one, a dollar amount in the other) — a unit mismatch with no structural safeguard against future confusion.
- Sales Reports and Dashboard Reporting, audited for the first time during this initiative (they were out of scope for the original CRM audit), were found to independently reimplement the same account-payment tax-extraction formula three times (correctly) and once incorrectly — the Dashboard's version currently produces numbers that do not reconcile with the Sales Tax and Pure Sales Summary reports for the same data.

### 4.3 Summary of CRM Billing Audit findings

The CRM Billing Payment Audit (`docs/crm-billing-audit/CRM_BILLING_PAYMENT_AUDIT.md`) was the origin of this initiative. It confirmed one customer-visible bug — a display-only double-counting of tax on the Billing Summary "Last Payment" column, already fixed and deployed — and, more importantly, established that this bug was a symptom of a structural problem: the tax-inclusion decision being re-implemented independently across the codebase rather than owned by a single authority. The audit's deeper findings (divergent balance computations, dual invoice-update paths, the unit mismatch, unverified delete-path integrity) are what this initiative — not a second bug fix — was scoped to address.

## 5. Target Architecture

The end state is four narrow, purpose-built services, each owning one financial domain, rather than one large monolith. This mirrors boundaries that already exist naturally in the data model (ledger rows, invoices, reporting, post-order charges), which is what makes independent, low-risk migration of each one possible.

### `TaxCalculationService`

The foundation. The single place in the system that answers "given this amount, this rate or tax amount, and this transaction context, what is the correct tax breakdown?" It is pure calculation — no database access, no side effects — which is what makes it trivially unit-testable and safe to build before anything depends on it. It replaces the tax-inclusion branch logic currently duplicated across `CustomHelper`'s four balance methods, the four duplicated Blade tax-breakdown views, and the account-payment tax formula currently triplicated (correctly) across the reporting engines and (incorrectly) in Dashboard reporting.

### `LedgerBalanceService`

Owns the customer running balance — both the stored, incrementally-updated column and the live-recomputed value — collapsing what are currently two independent computations into one. It wraps `TaxCalculationService` for the tax portion of every balance calculation and replaces the highest-blast-radius logic in the system: the methods responsible for applying, reversing, and repairing ledger transactions across every module that writes to the Credit Account ledger.

### `InvoiceCalculationService`

Owns invoice totals and the paid/open-amount lifecycle. It replaces both the existing aggregation method and the inline arithmetic currently duplicated in the invoice payment controllers, so that "how much of this invoice has been paid" is answered the same way regardless of which code path triggered the question.

### `FinancialReportingAdapter`

A thin, read-only adapter — not a new calculation engine — that lets Sales Reports and Dashboard Reporting consume `TaxCalculationService`'s formulas (exposed in a form usable both in PHP and in SQL aggregation, since reporting engines operate on large date ranges for performance) instead of each maintaining its own copy. It does not replace the Billing Engine, which already owns its own charge lifecycle and receives pre-computed tax amounts from its callers.

Together, these four services are designed so that every financial domain in §6 below eventually depends on one or more of them, and none of them depend on any domain-specific controller or view — the dependency arrow always points from feature code into the shared services, never the reverse.

Also fixed a latent rounding-order bug discovered in `TaxCalculationService` itself (zero production impact — the method had no prior callers). Full detail in `PHASE_2_2_COMPLETION_REPORT.md`; the deferred `SalesTaxReportEngine` migration is tracked as an open architectural task in `FINANCIAL_ENGINE_TODO.md`.
- **Phase 2.3 — Dashboard Financial Consistency** — fixed the confirmed Dashboard revenue/tax formula bug (`Dashboard\IndexController::getRevenueRows()`: multiplication → division). Discovered, and avoided, a second independent instance of the Phase 2.2 aggregation-order tension by adding a purpose-built unrounded method (`TaxCalculationService::extractBaseFromInclusiveAmountRaw()`) rather than forcing the rounded contract to fit; proved zero divergence from `SalesReportEngineV2`'s totals across 20,000 simulated dashboard periods. **Both confirmed production bugs identified by the original CRM Billing Audit are now fixed.** The business also approved **Financial Decision FD-001** (`FINANCIAL_DECISIONS.md`): transaction/line-level sales tax is the Financial Engine's source of truth, and reports must consume already-calculated values rather than independently recalculating tax from aggregated totals. As a direct consequence, **`SalesTaxReportEngine` is now officially deferred** to a future "Sales Tax Report V2" project — no phase of this initiative may modify it. Full detail in `PHASE_2_3_COMPLETION_REPORT.md`.
- **Phase 2.3A — Calculation Pattern Architecture** — formalized the pattern behind both Phase 2.2's and Phase 2.3's aggregation-order discoveries into two named calculation families, **Financial Transaction Calculations** and **Financial Analytics Calculations**, with explicit rules, a developer decision tree, and an API categorization of every `TaxCalculationService` method (`PHASE_2_3A_CALCULATION_PATTERN_ARCHITECTURE.md`). Financial Decision FD-001 was amended (not rewritten) to state four clarifying rules distinguishing compliant aggregation-order deferral from a policy violation. Accompanied by a small, additive, comment-and-test-only code change: `TaxCalculationService`'s methods now carry explicit "TRANSACTION-SAFE" / "ANALYTICS-ONLY" PHPDoc labels, and new tests make the distinction executable rather than only written. No business behavior changed. Full detail in `PHASE_2_3A_COMPLETION_REPORT.md`.

## 8. Risk Management

### Technical risks

The highest-blast-radius method in the system, `updateCreditBalance()`, has 26 known call sites spanning CRM, Invoicing, Dashboard, Orders, checkout, and the shared `ChargeService`. Any behavioral drift introduced while migrating it would affect real customer balances across every one of those modules simultaneously. This is the single largest technical risk in the initiative and is why it is scheduled last, migrated in module-scoped batches, and validated at every batch against a before/after ledger replay.

### Business risks

The tax treatment of Refunds and Discounts is not currently documented as an intentional business rule anywhere — it is only observable as four different pieces of code disagreeing with each other. Unifying this logic without explicit business sign-off risks silently encoding whichever behavior a developer happens to pick as "correct," which is the same failure mode that produced the original bug. This is treated as a hard gate (Phase 2.0), not a nice-to-have.

### Accounting risks

Any change to how tax, balances, or invoice totals are computed has the potential to alter historical or ongoing financial reporting in ways that are visible to customers and staff. The Dashboard tax-formula fix (Phase 2.3) is the clearest example: correcting it will visibly change previously-reported revenue figures for past periods if those figures are recalculated. Every phase that can produce a visible number change is treated as its own signed-off change, separate from pure code consolidation that is expected to produce zero visible difference.

### Migration risks

Consolidation phases that touch write paths (`InvoiceCalculationService`, `LedgerBalanceService`) carry the risk that a calculation which looks equivalent in code is not, in fact, equivalent for every historical data shape already in the database (edge cases in existing invoices or ledger rows that predate careful validation). This is mitigated by validating every write-path migration against a full snapshot of real data before and after the change, not just against newly-written test fixtures.

### Rollback philosophy

Every phase in this initiative is designed to be revertible on its own, independent of any other phase. Legacy methods are not deleted until every caller has been migrated and confirmed stable — they remain in place as thin wrappers throughout the transition specifically so that any individual phase can be reverted without needing to also revert phases that came after it. Rollback is treated as a first-class design constraint of each phase, decided before the phase starts, not improvised if something goes wrong.

### Validation strategy

Where a validation tool already exists — `FixRunningBalancesController`'s ledger-replay diff — it is reused rather than rebuilt, and is the primary safety mechanism for every phase that touches balance calculations. Where no such tool exists (invoice totals, reporting output), the equivalent discipline is applied manually: snapshot real output before a change, reproduce it exactly immediately after the change with no new data, and only then allow new behavior to take effect going forward.

## 9. Testing Strategy

Financial validation in this initiative operates at three levels, and all three are required — none is a substitute for another.

**Unit testing** covers each shared service's calculations in isolation, against explicit input/output tables derived from real, previously-confirmed scenarios (the original $150.00/$136.67/$13.33 example, the audit's sixteen enumerated test scenarios, and the business-confirmed Refund/Discount truth table). Unit tests exist to prove a formula is correct in isolation, independent of any integration concern.

**Reconciliation testing** proves that once a service is wired into a real code path, it produces the same real-world numbers as before the change, for real data — not just for hand-picked test fixtures. This is the before/after snapshot-and-diff discipline used throughout the Implementation Plan: run the calculation before a migration, run it again after, and require the result to be identical for every existing record, before allowing the new path to govern any new activity. Reconciliation is what proves "consolidation," not just "no crash."

**Regression testing** ensures that once two systems are supposed to agree (e.g. Dashboard Reporting and Sales Tax Reporting, or the stored and live-computed available balance), an automated test continues to assert that agreement going forward, so a future change cannot silently reintroduce the exact class of drift this initiative exists to eliminate. Every phase that unifies a previously-duplicated calculation should leave behind a regression test asserting the two (formerly divergent) call sites now agree — not just that each individually passes its own tests.

Automated testing is treated as a permanent investment, not a one-time migration gate: the value of these tests is highest years from now, when a future developer changes something adjacent and needs to be told immediately if they've reintroduced a divergence this initiative spent significant effort removing.

---

## 10. Success Criteria

This initiative will be considered successful when:

- Every financial number in the system — a tax amount, a balance, an invoice total, a revenue figure — has exactly one authoritative calculation, with no independent re-derivation anywhere else in the codebase.
- CRM, the Billing Engine, Invoicing, Dashboard Reporting, and Sales Reports always reconcile with one another for the same underlying data, as a structural guarantee rather than something that has to be separately verified after every change.
- The duplicate calculations inventoried in the CRM Billing Audit and the Phase 2 Architecture Report have been eliminated, not merely reduced.
- The four shared financial services are genuinely reusable — a new financial feature can be built by composing them rather than by writing new bespoke calculation logic.
- Financial bugs of the class that motivated this initiative — a correct underlying fact displayed or reported incorrectly because of duplicated logic — become significantly less frequent, and when they do occur, are fixable in one place rather than requiring a search across every duplicate implementation.
- New financial features are demonstrably easier and faster to implement correctly, because the hard part (tax rules, balance rules, invoice rules) is already solved and shared, not re-solved per feature.

## 11. Project Governance

All future work under this initiative — including work not yet planned as of this document's publication — must follow the same governance model that produced the audit, the architecture report, and the implementation plan:

- **Architecture review first.** No implementation phase begins without a written architecture rationale reviewed ahead of time. This document and its companions are the model to follow, not a one-time exception.
- **Small implementation phases.** Every change is scoped to be independently reviewable and independently mergeable. A change that cannot be described, validated, and rolled back on its own is scoped too broadly and must be split.
- **Independent validation.** Every phase states, in advance, how it will be proven correct — unit tests, reconciliation snapshots, or regression assertions — before it is merged, not after a problem is reported.
- **Separate documentation updates.** Architecture decisions, implementation plans, and this roadmap are kept current as living documents, not written once and left to go stale. A phase is not complete until its corresponding documentation has been updated.
- **Conservative deployment.** Changes that can alter visible financial output — even to fix a confirmed bug — are deployed with explicit business sign-off and are never bundled with unrelated consolidation work.
- **Rollback planning.** Every phase defines its rollback method before implementation begins, not as an afterthought if something goes wrong.

Any future contributor proposing to extend, accelerate, or deviate from this roadmap should treat these six requirements as non-negotiable process, not as guidance to be weighed against schedule pressure.

## 12. Living Document

This document is the master roadmap for the Financial Engine initiative and is intended to remain the single authoritative overview of the project for the lifetime of Kabba.

It must be updated whenever any of the following occurs:

- A planned phase from §7 is completed — move it from Planned to Completed, and summarize what changed and what was validated.
- A major architectural decision is made — a service boundary changes, a new financial domain is discovered, or a risk in §8 materializes and is resolved.

- A new financial domain or subsystem is introduced to Kabba — it should be added to §6 with its intended relationship to the shared Financial Engine stated explicitly, before it accumulates its own independent financial logic.

Future developers, architects, and auditors should be able to read this single document and understand, without needing to reconstruct history from commit logs or scattered tickets, why the Financial Engine exists, what it is designed to guarantee, how far the initiative has progressed, and what governs any future work on it.
